1. Executive Summary & Problem Formulation

In emergency medicine, the concept of the "Golden Hour" dictates that rapid medical intervention within the first 60 minutes following severe trauma, cardiac arrest, or stroke drastically reduces mortality and long-term morbidity rates. Traditional emergency dispatching mechanisms face recurring friction points:

  • Caller Anxiety & Verbal Miscommunication: Callers in distress struggle to provide accurate addresses, landmarks, or postal codes over cellular phone connections.
  • Manual Dispatch Bottlenecks: Control centers manually contact individual hospitals and ambulance stations through telephone trees, delaying deployment.
  • Siloed Fleet Visibility: Hospitals lack real-time visibility into mutual fleet availability and incoming trauma cases.
  • Driver Navigation Disconnect: Ambulance drivers rely on oral phone instructions without exact GPS navigation coordinates to the patient.
The Core Solution: The Smart Emergency Response & Ambulance Dispatch System creates a real-time, bi-directional emergency triage network. Citizens trigger zero-login GPS-pinned distress calls in under 5 seconds. The nearest participating hospital receives immediate catchment alerts and automatically assigns the closest available ambulance through the spherical Haversine geodesic algorithm. Drivers broadcast real-time telemetry updates as they transition from transit to patient pickup to hospital emergency room handover.

3. Comprehensive Module-by-Module Specification

The system is decomposed into 8 interconnected functional modules. Each module encapsulates dedicated business logic, user interface views, data models, and API contracts.

3.1 Module 1: Citizen / Patient Emergency Access Portal

Public / No Login

Component Files: frontend/src/components/CitizenEmergencyView.js, frontend/App.js (Expo entry), backend/Program.cs (/api/emergency).

Purpose & Philosophy: When a medical catastrophe occurs, users cannot be hindered by registration screens, password prompts, or email verifications. This module provides a friction-free, instantaneous gateway to emergency dispatch.

Key Functional Capabilities

  • Single-Tap GPS Acquisition: Queries device GPS sensors (via HTML5 Geolocation API on web or expo-location on native) to obtain precise Latitude and Longitude coordinates.
  • Offline "Call 108" Dial Link: Built-in tel:108 protocol trigger that directly opens the native phone dialer to reach national emergency services even when mobile internet data fails.
  • Triage Categorization: Rapid radio selectors for Emergency Type (Accident, Cardiac, Trauma, Respiratory, Maternal) and Priority level (Critical, Urgent, Normal).
  • Live Ambulance Tracker: Once submitted, polls the backend (every 5 seconds) to detect hospital acceptance, displaying vehicle license plate, driver phone, and live vehicle location on Leaflet map.

Data Inputs & Outputs

  • User Inputs: Patient Name, Phone Number, Emergency Type, Priority, GPS Coordinates (auto-filled).
  • Output / Feedback: Unique RequestId, status tracker badge (Pending -> Accepted -> En Route -> Arrived), ambulance contact details, and hospital name.
  • Native Feature: Camera QR Code scanner (CameraView) to auto-pair mobile apps to the hospital local LAN server.

3.2 Module 2: Hospital Command Center Portal

Role: Hospital

Component Files: frontend/src/components/HospitalDriverPortal.js, backend/Program.cs (/api/hospitals, /api/emergency/available-for-hospital/{id}, /api/emergency/{id}/accept).

Purpose & Philosophy: Empowers hospital staff to monitor incoming distress calls within their geographic catchment area and dispatch their private or affiliated ambulance fleet.

Key Functional Capabilities

  1. Hospital Authentication: Secure passwordless token generation verifying registered hospital contact telephone number (claims injected: Role: Hospital, hospitalId: X).
  2. Geofenced Emergency Feed: Backend automatically filters all active pending emergency requests. Using the Haversine formula, it only serves requests whose nearest hospital is this facility, preventing multi-hospital dispatch chaos.
  3. One-Click Dispatch Acceptance: Clicking "Accept Emergency" triggers an automated backend routine:
    • Finds the nearest Available ambulance belonging exclusively to this hospital.
    • Creates a new record in Dispatches table linking the Request, Ambulance, and Hospital.
    • Transitions Request status to Accepted by Hospital and Ambulance status to Assigned.
  4. Hospital Fleet Management: Add new ambulances (Vehicle Number, Driver Name, Driver Phone, Vehicle Type), view live fleet availability, and decommission units.
  5. Active Mission Tracking: Inspect assigned runs, see patient pickup location on map, and prepare emergency room staff prior to patient arrival.

Role: Driver

Purpose & Philosophy: Designed specifically for in-vehicle mounted tablets or driver mobile phones. Provides clear, high-contrast operational status and automated real-time GPS telemetry broadcasting.

Continuous GPS Telemetry

Mounts a background navigator.geolocation.watchPosition worker that triggers HTTP PUT requests to /api/ambulances/{id}/location every few seconds. This keeps the centralized system and patient tracking maps accurate within meters.

Lifecycle State Controller

Drivers interact with large, tactile buttons that progress the dispatch state:
Assigned → En Route → Arrived at Scene (records ArrivalTime) → Transporting → Completed (records CompletionTime, releases ambulance back to "Available").

Driver Mission HUD: Displays patient emergency priority badge (Critical / Urgent / Normal), patient contact phone with direct click-to-call link, address/landmark notes, patient GPS coordinates on interactive Leaflet map, and assigned destination hospital name.

3.7 Module 7: Core Geospatial & Dispatching Engine

Mathematical Engine

Component Files: backend/Program.cs (Haversine implementation, /api/ambulances/nearest, /api/hospitals/nearest).

The dispatching engine computes the great-circle geodesic distance between two points on the Earth's surface using latitude and longitude coordinates. This eliminates dependency on external paid map APIs for distance heuristics.

Spherical Haversine Mathematical Derivation:

Given two geographic points $P_1(\phi_1, \lambda_1)$ and $P_2(\phi_2, \lambda_2)$, where $\phi$ is latitude in radians and $\lambda$ is longitude in radians:

Δφ = (lat2 - lat1) * π / 180
Δλ = (lon2 - lon1) * π / 180
a  = sin²(Δφ / 2) + cos(φ1) * cos(φ2) * sin²(Δλ / 2)
c  = 2 * atan2(√a, √(1 - a))
d  = R * c  (where Earth mean radius R = 6,371,000 meters)

C# Optimization: The backend computes Distance(lat1, lon1, lat2, lon2) in pure double-precision floating-point arithmetic. LINQ OrderBy(a => Distance(...)).FirstOrDefault() executes within microseconds over in-memory or cached fleets.

6. Algorithmic Formulations & Mathematical Modeling

The dispatch intelligence hinges on two algorithmic pipelines: Geodesic Proximity Optimization and Hospital Catchment Partitioning.

6.1 Great-Circle Geodesic Distance (Haversine)

Standard Euclidean distance ($\sqrt{\Delta x^2 + \Delta y^2}$) produces severe spherical distortion over geographical coordinates. The Haversine formulation calculates great-circle distances over Earth's spherical geoid:

Let $R = 6371 \times 10^3\text{ meters}$ (mean radius of Earth). For coordinates $(\text{lat}_1, \text{lon}_1)$ and $(\text{lat}_2, \text{lon}_2)$ converted to radians:

$$\Delta\phi = (\text{lat}_2 - \text{lat}_1) \cdot \frac{\pi}{180}, \quad \Delta\lambda = (\text{lon}_2 - \text{lon}_1) \cdot \frac{\pi}{180}$$ $$a = \sin^2\left(\frac{\Delta\phi}{2}\right) + \cos(\phi_1)\cos(\phi_2)\sin^2\left(\frac{\Delta\lambda}{2}\right)$$ $$c = 2 \cdot \text{atan2}\left(\sqrt{a}, \sqrt{1-a}\right)$$ $$d = R \cdot c$$

6.2 Hospital Catchment Partitioning Algorithm

To prevent multiple hospitals from simultaneously deploying ambulances to the same victim, the system executes an automated spatial partition when querying pending cases:

Algorithm CatchmentPartition(Hospital H_current, List<Hospital> OpenHospitals, List<EmergencyRequest> PendingRequests): Initialize AvailableList = [] For each Request R in PendingRequests: NearestHospital = null MinDistance = +Infinity For each Hospital H in OpenHospitals: Dist = Haversine(R.Latitude, R.Longitude, H.Latitude, H.Longitude) If Dist < MinDistance Then: MinDistance = Dist NearestHospital = H // Only include if THIS hospital is the absolute closest facility to the patient If NearestHospital.HospitalId == H_current.HospitalId Then: AvailableList.Add(R) Sort AvailableList ascending by Haversine(H_current, R) Return AvailableList

7. Dispatch State Machine & Operational Lifecycle

An emergency incident progresses through a strict, deterministic finite state machine (FSM). State changes are validated across relational entities to guarantee operational consistency.

[ CITIZEN DISTRESS ] | v ( Status: Pending ) <---------------- Patient submits GPS & triage category | | Hospital accepts request via /api/emergency/{id}/accept v ( Status: Accepted by Hospital ) ( Ambulance: Assigned ) <----------- Nearest available hospital ambulance paired | | Driver taps "Start Route" in mobile console v ( En Route ) <------------------- Driver navigating to patient; continuous GPS sync | | Driver taps "Arrived at Scene" v ( Arrived at Scene ) <---------------- ArrivalTime timestamp recorded in DB | | Patient stabilized; transporting to trauma center v ( Transporting ) | | Patient admitted to Emergency Room; Driver taps "Complete" v ( Completed ) <------------------- CompletionTime timestamp recorded; Ambulance reset to "Available"

8. Deployment, Setup & Smoke Verification Guide

The system is pre-configured to run out of the box in development environments with zero setup friction, featuring automatic database fallback and dual frontend runtimes.

8.1 Backend Configuration (.NET Minimal API)

1. Open a PowerShell terminal and navigate to the backend directory:

cd d:\new_project\backend
dotnet restore
dotnet build

2. Run database migrations (optional; if SQL Server is absent, the backend automatically activates the In-Memory database provider):

dotnet ef database update

3. Start the backend server (binds to http://0.0.0.0:5000 to allow mobile LAN devices to connect):

dotnet run

4. Verify Swagger OpenAPI documentation at: http://localhost:5000/swagger

8.2 Frontend Configuration (React / Expo)

1. Open a second PowerShell terminal in the frontend directory:

cd d:\new_project\frontend
npm install
npm start

2. Press w in the Expo terminal to launch the Desktop Command Center Web Console in your default web browser (at http://localhost:8081).

3. For mobile testing on physical Android or iOS phones, open Expo Go and scan the terminal QR code, or use the camera QR scanner inside the app to pair with your computer's IP address.

8.3 Automated Smoke Verification Script

The repository includes an end-to-end automated PowerShell integration smoke test located at tests/smoke_test.ps1. To execute full test verification:

pwsh -File d:\new_project\tests\smoke_test.ps1

The script validates: Admin authentication → Hospital creation → Ambulance creation → Emergency submission → Haversine nearest search → Dispatch pairing → Call log recording → Dispatch verification.
