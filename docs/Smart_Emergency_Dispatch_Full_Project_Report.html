Chapter 1: Project Overview & Problem Formulation

1.1 The Critical "Golden Hour" in Emergency Medicine

In emergency clinical medicine, the period immediately following traumatic injury or acute systemic distress—such as myocardial infarction (heart attack), cerebrovascular stroke, or massive hemorrhage—is designated as the "Golden Hour". Extensive epidemiological studies demonstrate that patients who receive definitive emergency medical care within this 60-minute window exhibit a survival probability up to 300% higher than those whose intervention is delayed. Every passing minute without clinical resuscitation or oxygenation causes irreversible tissue necrosis, neuronal damage, and permanent functional impairment.

1.2 Inadequacies in Traditional 108 Emergency Workflows

In India, the primary emergency medical infrastructure is governed by the national 108 Ambulance Service. While this network provides broad geographical reach, the underlying operational workflow depends heavily on manual telephonic coordination, resulting in substantial friction:

  • Verbal Location Ambiguity: When a distressed citizen dials 108, the dispatcher relies on verbal descriptions of landmarks, street names, and directions. In unfamiliar locations, high-stress situations, or rural areas, communicating an exact location takes an average of 2.5 to 4.5 minutes, frequently leading to navigational errors.
  • Absence of Pre-Arrival Guidance: While the ambulance is in transit (typically 15 to 25 minutes), bystanders and family members are left without structured clinical guidance. Life-threatening conditions like sudden cardiac arrest require immediate Chest Compressions (CPR); without guidance, bystander CPR rates remain below 2% in developing urban centers.
  • Hospital ER Blindness: Conventional ambulances operate as "black boxes". Hospital Emergency Rooms (ERs) receive zero advance notice of the patient's physiological state (heart rate, blood pressure, oxygen saturation, trauma level) until the ambulance physically enters the triage bay. This creates a critical 10-to-15-minute intake bottleneck while trauma teams scramble to prepare ventilators, blood products, and surgical suites.
  • Municipal Traffic Congestion: Ambulances frequently get trapped in dense urban traffic intersections. While sirens offer localized warnings, traffic signals remain uncoordinated, causing severe transit bottlenecks.

1.3 Proposed System Solution & Value Proposition

To eradicate these systemic inefficiencies, the Smart Emergency Response & Ambulance Dispatch System introduces a modernized, multi-tier software infrastructure built upon contemporary web and mobile technologies:

Chapter 2: Literature Survey & Comparative Analysis

2.1 Existing EMS Implementations

An in-depth survey of existing emergency medical dispatch technologies reveals distinct architectural generations:

  • Traditional 108 CAD Systems (India - EMRI GVK): Dependent on voice telephony, call queues, and manual GIS plotting. While effective for nationwide aggregation, call-taking latency remains high, with no automated digital bystander feedback.
  • E-911 & NG-911 (United States): Employs Automatic Location Identification (ALI) via cellular triangulation. While accurate, the systems require proprietary carrier hooks, complex public safety answering points (PSAPs), and lack pre-arrival video or audio CPR rhythm guidance for citizens.
  • Commercial Ride-Hailing Adaptation (Uber Health / Lyft Pass): Focuses primarily on non-emergency scheduled patient transport. Lacks emergency prioritization, medical triage classifications, vital sign telemetry, and hospital ER integration.

4.2 Reverse Proxy & Multi-Server Mesh Implementation

The frontend mesh is served by a custom Node.js reverse proxy server (multi-server.js) executed via start_all_ui.ps1. The server initializes 4 HTTP listeners simultaneously. Any incoming request with path prefix /api/* across any port is automatically intercepted and reverse-proxied to the backend at http://localhost:5000, eliminating CORS friction while preserving cookie and authorization headers.

5.3 Automatic Database Failover Architecture

In high-stakes emergency dispatch systems, server startup must never crash due to database connection latency or localized SQL Server outages. The system implements a resilient connection probe in Program.cs: 

// Dynamic SQL Server verification with In-Memory failover fallback
var useInMemory = false;
try {
    using var testConn = new SqlConnection(defaultConn);
    testConn.Open();
    testConn.Close();
} catch {
    useInMemory = true;
}

if (!useInMemory) {
    builder.Services.AddDbContext<AppDbContext>(opt => opt.UseSqlServer(defaultConn));
} else {
    // Seamless in-memory provider activates automatically
    builder.Services.AddDbContext<AppDbContext>(opt => opt.UseInMemoryDatabase("SmartDispatchInMemory"));
}

Chapter 6: Algorithmic Formulations & Mathematical Modeling

6.1 Great-Circle Spherical Haversine Geodesic Distance

Standard planar Euclidean distance ($\sqrt{\Delta x^2 + \Delta y^2}$) produces severe spherical distortions over geographical coordinates on the Earth's ellipsoidal surface. To compute accurate geodesic proximity between an emergency incident and emergency vehicles, the system applies the Spherical Haversine Equation:

Let Earth's mean volumetric radius be $R = 6,371 imes 10^3 ext{ meters}$. For coordinates $(\phi_1, \lambda_1)$ and $(\phi_2, \lambda_2)$ in radians:

$$\Delta\phi = ( ext{lat}_2 - ext{lat}_1) \cdot rac{\pi}{180}, \quad \Delta\lambda = ( ext{lon}_2 - ext{lon}_1) \cdot rac{\pi}{180}$$ $$a = \sin^2\left( rac{\Delta\phi}{2} ight) + \cos(\phi_1)\cos(\phi_2)\sin^2\left( rac{\Delta\lambda}{2} ight)$$ $$c = 2 \cdot ext{atan2}\left(\sqrt{a}, \sqrt{1-a} ight)$$ $$d = R \cdot c$$

This formula is natively executed in C# within the nearest ambulance search endpoint: 

private static double HaversineDistance(double lat1, double lon1, double lat2, double lon2) {
    var R = 6371e3; // Earth radius in meters
    var phi1 = lat1 * Math.PI / 180;
    var phi2 = lat2 * Math.PI / 180;
    var deltaPhi = (lat2 - lat1) * Math.PI / 180;
    var deltaLambda = (lon2 - lon1) * Math.PI / 180;

    var a = Math.Sin(deltaPhi / 2) * Math.Sin(deltaPhi / 2) +
            Math.Cos(phi1) * Math.Cos(phi2) *
            Math.Sin(deltaLambda / 2) * Math.Sin(deltaLambda / 2);
    var c = 2 * Math.Atan2(Math.Sqrt(a), Math.Sqrt(1 - a));
    return R * c; // Distance in meters
}

6.2 Hospital Catchment Spatial Partitioning Algorithm

To prevent multiple hospital facilities from simultaneously deploying ambulances to the exact same incident, the system executes an automated spatial partition algorithm:

Catchment Partitioning Logic
An emergency request $R$ is visible in the dispatch intake queue of Hospital $H_{ ext{current}}$ if and only if: $$ ext{Haversine}(R, H_{ ext{current}}) = \min_{H_i \in ext{OpenHospitals}} \left\{ ext{Haversine}(R, H_i) ight\}$$

Chapter 7: Deep-Dive Module Implementation

7.1 Port 3001: Citizen Emergency SOS Portal & Audio-Visual CPR Metronome

The citizen portal prioritizes immediate access under extreme psychological distress. Key implemented features include:

  • Zero-Login Architecture: The user is not required to create an account, enter passwords, or verify OTPs. Accessing port :3001 immediately requests high-accuracy browser geolocation.
  • 8 Standardized Medical Classifications: Fast one-touch cards for Cardiac Arrest, Trauma/Accident, Respiratory Distress, Stroke / Neurological, Severe Bleeding, Burn Injury, Poisoning / Overdose, and Obstetric / Pediatric.
  • Synthesized Audio-Visual CPR Metronome: Developed using the browser's AudioContext Web Audio API, generating a crisp 800 Hz acoustic tone at 110 BPM (matching the American Heart Association recommended rhythm of 100-120 compressions per minute). Accompanied by a pulsating high-visibility visual animation instructing bystanders: "Push hard and fast in the center of the chest (5 cm deep)".
  • Direct Offline 108 Helpline Integration: A persistent <a href="tel:108"> button that functions even when data connectivity is degraded.

7.2 Port 3002: Paramedic Mobile MDT & Pre-Hospital Vitals Telemetry Uplink

The ambulance console serves as an in-vehicle Mobile Data Terminal (MDT):

  • 5-Stage Mission Lifecycle: Drivers advance missions deterministically through Assigned → En Route → Arrived at Scene → Transporting → Completed.
  • Continuous GPS Broadcast: Automatically emits the vehicle's real-time position to the backend, enabling live route tracking for both the citizen and command center.
  • Pre-Hospital Vitals Telemetry Uplink: Paramedics record vital signs in transit:
    • Heart Rate (e.g., 108 BPM)
    • Blood Pressure (e.g., "128/84 mmHg")
    • Oxygen Saturation SpO2 (e.g., 95%)
    These are transmitted via POST /api/dispatch/{dispatchId}/vitals and immediately streamed to the receiving hospital.

7.3 Port 3002: Hospital ER Trauma Board & Bed Occupancy Management

The hospital ER interface displays a live dashboard of incoming trauma cases:

  • Incoming Patient Telemetry Board: Displays patient demographic details, triage category, assigned ambulance, and latest telemetry vitals uplinked from the ambulance in transit.
  • Trauma Bed Management: Real-time toggle controls for critical emergency beds:
    • ICU Emergency Bed (Occupied / Available)
    • Trauma Bay 1 (Occupied / Available)
    • Trauma Bay 2 (Occupied / Available)

7.4 Port 3003: Tactical Command Center, Green Corridor & Analytics

Designed for city-wide municipal emergency coordination:

  • Tactical GIS City Map: Renders active emergency markers (red), available ambulances (green), en-route ambulances (amber), and hospital trauma centers (blue).
  • 1-Click Auto-Dispatch Engine: Invokes the C# Haversine nearest-vehicle calculation and binds the optimal ambulance instantly.
  • Municipal Green Corridor Switchboard: Toggles an emergency preemption state to coordinate with municipal traffic management and clear intersections along the ambulance route.
  • Analytics & Audit Logs: 24-hour demand heat curve charts, emergency classification distribution, and searchable mission audit log with instant CSV export.

7.5 Port 3000: Master Mission Control Hub & Multi-Server Mesh

The master launcher links all operational portals with live port health monitoring. A persistent top navigation banner across all interfaces enables single-click role switching during multi-window demonstrations.

Chapter 8: Security Architecture, RBAC & API Reference

8.1 JWT Claims-Based Authentication & HMAC-SHA256 Signing

Administrative, driver, and hospital endpoints are protected by JSON Web Tokens (JWT). The backend enforces a minimum 256-bit (32-byte) cryptographic key:

  • Token Claims: Tokens embed ClaimTypes.NameIdentifier, ClaimTypes.Email, and ClaimTypes.Role.
  • Authorization Policies: AdminOnly requires Role="Admin"; DriverOnly requires Role="Driver"; HospitalOnly requires Role="Hospital".
